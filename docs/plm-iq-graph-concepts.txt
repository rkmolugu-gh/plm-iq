PLM-IQ GRAPH CONCEPTS

CORE VOCABULARY
Node = PLM business object
Edge = directed connection between nodes
Edge Type = semantic meaning of an edge
Edge Property = structured data carried by an edge
Edge Annotation = human/AI commentary on an edge
Edge Evidence = source supporting an edge or conclusion
Edge Impact = assessed effect of a change
Graph Traversal = navigation through edges
Path = sequence of nodes and edges
Subgraph = selected graph region
Neighborhood = directly connected nodes
Upstream = contributing/source nodes
Downstream = dependent/affected nodes
Lineage = derivation/history path
Traceability = connected cross-domain path
Impact Set = candidate affected nodes
Change Propagation = traversal of impact through the graph

GRAPH TRAVERSAL
Direct neighbors = nodes one edge away
Upstream traversal = source/contributing dependencies
Downstream traversal = dependent/affected nodes
Dependency traversal = follow DEPENDS_ON
Structure traversal = follow HAS_COMPONENT/HAS_SUBASSEMBLY
Traceability traversal = Requirement -> Product -> CAD -> Drawing -> Test -> Change
Change propagation = changed node -> relevant edges -> impacted nodes -> further traversal

GRAPH GOVERNANCE
1. Store one canonical direction for each semantic edge.
2. Define inverse edge types instead of duplicate edges.
3. Keep authoritative domain data in domain tables.
4. Use the graph as the relationship/traceability layer.
5. Preserve history for controlled PLM edges.
6. Distinguish human assertions from AI inference.
7. Require evidence for AI impact conclusions.
8. Do not allow an LLM to directly mutate authoritative graph state.
9. Govern edge types centrally.
10. Apply tenant security to nodes and edges.

CONCEPTUAL MODEL
(Graph tables use the plmiq prefix; domain data stays in the existing domain tables.)

plmiq_node  (polymorphic node registry -> any existing domain object)
  |
  +-- plmiq_edge --+-- plmiq_edge_type
  |                +-- edge_properties
  |                +-- plmiq_edge_annotation
  |                +-- plmiq_edge_evidence
  |                +-- plmiq_edge_impact
  |
  +-- domain object tables (unchanged)

PLM-IQ PRINCIPLE
Nodes represent WHAT exists.
Edges represent HOW things are connected.
Edge properties represent structured relationship facts.
Edge annotations represent WHY the relationship matters.
Edge evidence represents WHY we believe it.
Impact assessments represent WHAT a change means.
AI agents reason over the graph but do not own authoritative truth.

================================================================================
GRAPH TERMINOLOGY — GROUNDED TO PLM-IQ BUSINESS OBJECTS
================================================================================

This section maps the conceptual vocabulary above onto the business objects that
already exist in PLM-IQ (tables in db/schema.sql, models in app/models/). Phase 1
builds the graph schema ONLY for these existing objects — no new business-object
tables are introduced. The graph is the relationship/traceability layer on top of
the authoritative domain tables (see GRAPH GOVERNANCE, items 3 and 4).

GROUNDING MATRIX

  Graph concept                            Existing PLM-IQ object (table)
  ---------------------------------------  -----------------------------------------------
  PART / ASSEMBLY node                     parts (role implied by BOM structure)
  HAS_COMPONENT / USED_IN edge             bom (parent_assembly -> part_number)
  COST node / COST_ELEMENT edge            costing_bom (per-part cost rows)
  ENGINEERING_CHANGE node                  engineering_change_orders
  AFFECTS / CHANGES edge                   engineering_change_orders.part_number -> parts
  SUPPLIER edge (manufactures/supplies)    approved_manufacturer_list, approved_vendor_list
                                           (AML = who MAKES, AVL = who SUPPLIES, -> parts)
  CAD_MODEL node / HAS_CAD edge            cad_metadata -> parts
  DOCUMENT node / HAS_DOCUMENT edge        documents -> parts
  WORKFLOW nodes/edges                     workflow_definitions, workflow_instances,
                                           workflow_tasks (OPERATES_ON, ASSIGNED_TO)
  USER / ORGANIZATION nodes                users, tenants (OWNS / RESPONSIBLE_FOR)
  -----------------------------------------------------------------------------------------
  Out of graph scope (Phase 1)             favorites, saved_queries, app_settings, roles

================================================================================
5-PHASE IMPLEMENTATION PLAN
================================================================================

Implemented incrementally, one phase per effort. Phase 1 is the schema; later
phases layer population, traversal, the agent, and hardening on top.

SCHEMA DECISION (applies to all phases)
- NORMALIZED INVERSE-FK NODE REGISTRY: plmiq_node is an IDENTITY-ONLY registry
  (node_id, label, attributes, audit, tenant) — NO type is stored on the node.
  The type of a node is derived from the business object that owns it: every
  node-capable domain table carries a UNIQUE nullable node_id FK to plmiq_node
  (parts, costing_bom, engineering_change_orders, AML, AVL, cad_metadata,
  documents, workflow_definitions/instances/tasks, users, tenants). This keeps
  object type on the business object and avoids duplicating it on the node. The
  graph is a relationship/traceability layer over authoritative domain tables
  (GRAPH GOVERNANCE items 3 and 4).
- All six core tables shipped in Phase 1, prefixed plmiq: plmiq_node,
  plmiq_edge_type, plmiq_edge, plmiq_edge_annotation, plmiq_edge_evidence,
  plmiq_edge_impact.
- Every graph table carries tenant_id + tenant_key, matching existing conventions,
  and is read/written only through TenantScopedSession (app/database.py) so
  tenant isolation is enforced centrally.

--------------------------------------------------------------------------------
PHASE 1 — GRAPH SCHEMA (terminology + six core plmiq tables)
--------------------------------------------------------------------------------
Create the schema for existing business objects only.
- db/schema.sql: add plmiq_node, plmiq_edge_type, plmiq_edge, plmiq_edge_annotation,
  plmiq_edge_evidence, plmiq_edge_impact plus indexes on
  (object_type, object_id), (source_node_id), (target_node_id), tenant columns.
- app/models/graph.py (+ register in app/models/__init__.py): SQLAlchemy models
  following existing conventions (Base from app/database.py).
  - plmiq_node: node_id PK, node_label, attributes (JSON), created_by/at,
    tenant_id, tenant_key. Identity-only: the owning domain row (each carries a
    UNIQUE node_id FK) supplies the object type.
  - Add node_id (Integer, UNIQUE, FK -> plmiq_node.node_id) to each node-capable
    domain table (parts, costing_bom, engineering_change_orders, AML, AVL,
    cad_metadata, documents, workflow_definitions/instances/tasks, users,
    tenants) so a node's type is derived from its business object.
  - plmiq_edge_type: id, name (unique), description, canonical_direction,
    inverse_type, is_active, tenant_key.
  - plmiq_edge: id PK, source_node_id, target_node_id (FK -> plmiq_node.node_id),
    edge_type_id (FK -> plmiq_edge_type.id), state, quantity, unit, sequence,
    attributes (JSON), created_by/at, updated_by/at, tenant_id, tenant_key
    (mirrors the EDGE PROPERTIES list).
  - plmiq_edge_annotation: id, edge_id (FK), annotation_type (GENERAL/ENGINEERING/
    RATIONALE/DECISION/WARNING/ASSUMPTION/IMPACT/REVIEW/AI_ANALYSIS/CUSTOMER/
    SUPPLIER/MANUFACTURING/QUALITY/COMPLIANCE), text, author_type (human|ai),
    created_by/at, tenant_id, tenant_key.
  - plmiq_edge_evidence: id, edge_id (FK), evidence_type (SOURCE_OBJECT/
    DRAWING_FEATURE/BOM_RECORD/WORKFLOW_RECORD/USER_ASSERTION/AI_INFERENCE/...),
    reference, confidence, created_by/at, tenant_id, tenant_key.
  - plmiq_edge_impact: id, edge_id (FK), impact_type (DIRECT/DOWNSTREAM/UPSTREAM/
    POTENTIAL/NO_IMPACT/UNKNOWN), impact_level, confidence, reason,
    analysis_method, evidence_count, reviewed, review_decision, analysis_run_id,
    tenant_id, tenant_key.
- Seed plmiq_edge_type with the edge types listed under "EDGE TYPES ... APPLICABLE
  TO EXISTING OBJECTS" above (incl. inverse_type values).
- Verify: rebuild DB via db/_build_db.py; confirm all six tables + seed edge types.

--------------------------------------------------------------------------------
PHASE 2 — POPULATE NODES & EDGES FOR EXISTING DATA (backfill/seeding)
--------------------------------------------------------------------------------
Register existing domain rows as nodes and derive edges from existing relational
links; do not invent new relationships.
- Backfill script (e.g. db/indexing/build_graph.py, following build_parts.py etc.):
  - Insert plmiq_node rows for parts, costing_bom, engineering_change_orders, AML,
    AVL, cad_metadata, documents, workflow definition/instance/task, users, tenants.
  - Derive edges: bom -> HAS_COMPONENT/USED_IN; ECO.part_number -> AFFECTS/CHANGES;
    AML/AVL -> HAS_SUPPLIER/HAS_VENDOR; cad_metadata/docs -> HAS_CAD/HAS_DOCUMENT;
    workflow instance/task -> OPERATES_ON/ASSIGNED_TO; user ownership.
  - Insert one plmiq_edge_evidence row per derived edge pointing at the source
    domain record (evidence_type=SOURCE_OBJECT / BOM_RECORD / etc., confidence
    defaulted for structural links).
- Respect canonical-direction + inverse-type governance; store human structural
  edges distinctly from future AI-inferred edges (GRAPH GOVERNANCE item 6).
- Verify: node/edge counts match domain counts; FK/tenant checks clean.

--------------------------------------------------------------------------------
PHASE 3 — GRAPH SERVICE & QUERY LAYER
--------------------------------------------------------------------------------
Expose read-only traversal over the graph, tenant-scoped via TenantScopedSession.
- New package app/graph/ with query/service functions:
  neighborhood(node), upstream(node), downstream(node), structure_traversal (follow
  HAS_COMPONENT), traceability_traversal (Requirement->Product->CAD->Drawing->Change
  as applicable to existing data), path(source, target), subgraph(nodes).
- FastAPI router app/routers/graph.py (mirrors existing router patterns) for the
  queries above; register in app/__init__.py / main app.
- Add MCP read-only graph tools to plm_mcp/server.py (and the shared tool registry
  if shared) so MCP clients can traverse the graph.
- Add unit tests for traversal directions and tenant scoping.

--------------------------------------------------------------------------------
PHASE 4 — IMPACT ANALYSIS AGENT
--------------------------------------------------------------------------------
An agent that understands the graph concepts (nodes, edge types, upstream/
downstream, lineage, traceability) and answers questions about relationships and
change impact.
- New module app/plmassistant/impact_agent.py modeled on assistant_agent.py
  (ReAct loop via chat_with_tools) with its own system prompt covering the graph
  vocabulary in this document + evidence-backed answering rules (answer only from
  tool data; distinguish structural edges from AI inference; require evidence for
  impact conclusions — PLM-IQ PRINCIPLE / GRAPH GOVERNANCE items 6-8).
- Graph tools added to the tool registry (plm_tools.py) reusing Phase 3 service
  functions: traverse, get_neighborhood, walk_upstream, walk_downstream,
  find_path, get_impact_set. Each deny-by-default on missing tenant_key, like the
  existing execute_tool gate.
- Impact assessment writes go to plmiq_edge_impact via human/AI review, never
  direct LLM mutation of authoritative state (GRAPH GOVERNANCE item 8).
- Router endpoint app/plmassistant/impact_router.py mirroring assistant_router.py;
  optionally surface the agent in MCP.
- Add integration tests: relationship questions resolve to correct edges/rows;
  cross-tenant questions are denied.

--------------------------------------------------------------------------------
PHASE 5 — VERIFICATION, TESTS & DOC FINALIZATION
--------------------------------------------------------------------------------
- Full test pass: schema (Phase 1), population integrity (Phase 2), traversal +

- Security review: confirm every graph code path is tenanted (deny-by-default),
  and no LLM can mutate authoritative domain tables through graph tools.
- Performance review: indexes on the new tables; bound traversal depth/width.
- Fold the completed phases back into this doc as the live implementation roadmap
